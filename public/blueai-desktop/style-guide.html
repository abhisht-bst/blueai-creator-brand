Modern Terminal — Design System

Every specimen on this page is the real component, rendered with the real class names from blueai-desktop.css — the same stylesheet the product links. Nothing is re-implemented here, so this page cannot silently drift from what ships. Token values are read live via getComputedStyle rather than typed in.

How the theming works. The --bai-* tokens (the swatch grid and scale tables below tally them live) are declared on .drawer (dark) and .drawer.light, not on :root — deliberately, because the dormant marketing site in this same repo uses the same --bai-* namespace with entirely different values, and the scoping is what stops the two colliding. Component rules are plain global classes that resolve those vars, so a specimen outside a token scope would lose every colour. This page wraps each canvas in .bai-scope — a tokens-only alias declared alongside .drawer in the product stylesheet, so these swatches are the real values, not a copy.

Color tokens

Grouped by role — the swatch grid below renders every token in the hand-curated GROUPS list, and a warning appears if the stylesheet declares a colour token the list forgot (the count lives in the grid, not this sentence: a hard-coded “46” here went stale when 5 tokens joined). Values are resolved from the live stylesheet for the currently selected specimen theme — flip Specimens above to compare dark against light. Tokens marked fixed are intentionally not redefined in light theme.

Icons

Feather-style line icons, built by the product's own iconSvg(path, size) helper: fill:none, stroke:currentColor, stroke-width:1.8, round caps and joins, 24×24 viewBox. They inherit colour from their container, which is why the same glyph works on a card, a button, and an accent chip without variants. The paths live in blueai-icons.js, which both the product and this page read from — so the grid below is the complete real inventory, not a sample.

Inconsistencies, recorded not tidied — each would be a product change, so they're documented rather than quietly fixed:

1. Stroke weights are not unified. iconSvg() renders at 1.8, but the product authors eight distinct weights file-wide (1.3 / 1.4 / 1.6 / 1.7 / 1.8 / 2 / 2.2 / 2.4), five of them on the static header/sidebar nodes (gear+help 1.6, sidebar nav 1.7, chevron/search 2, search-clear 2.2). Every glyph in the grid below is drawn at 1.8, so several render marginally lighter or heavier here than in the product. (An earlier version of this note said "four weights" — counted, it was eight; see the same correction in blueai-icons.js's header.)

2. Two close glyphs. close and closeAlt are different paths for the same X, both live today.

3. Convention-breakers carry metadata. The account "kebab" (fill-based, no stroke), the newChat bubble (filled, 100×100) and the three win* titlebar controls (10×10, per-element styling) don't fit the stroked-24×24 wrapper, so each has a BAI_ICON_META entry and icon() renders it on its own terms. (An earlier version said the kebab "isn't in the set and stays inline" — true until batch 3 named every glyph; the App-shell specimens above now consume all five by name.)

The ✦ sparkle is also absent by design: the product uses the text character, not an SVG, so it belongs to the type layer.

CONTROL BOX SHAPES — why each container is the shape it isThe designer's question (2026-08-10), asked of the Skills toolbar and of Claude's own desktop chrome: why is one hover container square, another rectangular, another slightly portrait — and what is the reason for each? The answer is that shape is never the decision. A control's box is its content plus one uniform padding, with the cross-axis size set by the row it sits in; the aspect ratio is what falls out of those two choices. Text is wide, so a text control is landscape. A glyph as wide as the row allows comes out square. A narrower glyph under the same side padding comes out slightly portrait — which is exactly why Claude shows rectangles on “Opus 5”/“High”, a square on the circular credits gauge, and marginally portrait boxes on its mic and chevron. Nobody picked those shapes. What IS a decision is which axis to be generous on, and Fitts settles it: the cost of acquiring a target depends on its extent along the direction the pointer approaches from. In a horizontal toolbar the pointer arrives horizontally — so WIDTH decides whether the click lands, and height is the cheap axis. In a vertical list it is precisely reversed. Hence the law (taste rule 48), enforced at runtime by icon-target-audit.js: an icon-only control in a horizontal row must be at least square; landscape is fine and sometimes better; portrait is a defect, because it spends the free axis and starves the deciding one. Floor of 22px — this app's own smallest deliberate control, not an imported number — on the travel axis for everything, and on both axes for icon-only controls. The reason for each family, then:
• .bai-icbtn 24×24 — square: a 14px glyph with uniform padding in a row that isn't taller than that. Header, back buttons, new-chat.
• .bai-list-head.with-search .bai-help-inline 32×32 — square, but derived: the toolbar stretches it to the search field's 32px height (rule 45, one toolbar = one control height) and aspect-ratio: 1 makes the width follow, so it stays square if that row's height ever changes. This one was the bug — 24×32, the app's only portrait control, because an earlier fix released height for the stretch and left width: 24px behind. The 8px it needs comes out of .bai-search, which is flex: 1.
• .bai-tb-btn 26×22 — landscape on purpose. OS window controls, and wider is strictly better on the travel axis. Not an inconsistency with the squares above; the same law with a different padding.
• .tgm-close 28×28, .bai-send / .bai-fb-btn / .bai-dt-navbtn 22×22 — square, at two densities: 28 where the row is a modal header, 22 where the context is tight. 22 is the floor, which is why it is also the smallest of these.
• .bai-menu-help 22×22 — square, corrected 2026-08-10 from a padding-sized 18.7×16 that was under the floor on both axes at once. Its menu header grew 26→32px as a result, which incidentally brought it in line with the 28px menu items.
• .bai-title-btn 306×24 — landscape, because it is a text control; the width was never the problem. Corrected from 306×14, the smallest control in the app, via vertical-only padding — horizontal padding would have shifted the title text for no target gain. Its 42px row absorbed it, so no pixel of text moved.
• .bai-side-item, .bai-menu-item, .bai-cat-row, .bai-set-row — full-width landscape, and that is the correct shape here: these sit in vertical lists, where the pointer travels vertically, so height is the deciding axis and full width is free.
• .bai-tgl 28×16 — the one real exception, and it is listed rather than silently skipped. A switch depicts a track with a knob travelling along it: that landscape IS the control, not a padding outcome. The audit whitelists it by name, and anything added to that whitelist must be a shape that means something.
• #baiModelBtn 61×20 — landscape text control whose cheap axis is 2px under the floor, because .bai-status declares height: 20px and a control cannot sensibly be taller than its own strip. Reported by the audit as INFO, never silently exempted — an exception that leaves no trace is how a floor quietly dies.

Form controls

Every control renders all its states — an input that looks identical empty and filled, or a toggle you can't read at a glance, is not finished.

.bai-seg .bai-seg-btn .fillSegmented control for 2–4 mutually exclusive options (this said "2–3" while the 4-across Repeat Type sentence and specimen were appended below it — corrected 2026-08-03). .active fills with accent — colour only, never metrics: no weight or size change, because the options are equal-width and a wider glyph would resize the whole row when you selected it (taste rule 41, learned from the skill-switcher reflow). .fill stretches the control to its container's width and divides it evenly (flex: 1), for a seg that has to line its edges up with full-width fields above it. Date & time picker

A two-step picker: choose a date, then a time. That structure is the whole design decision — an earlier version showed calendar and clock side by side and needed re-tuning for every width (oval day cells, overflow below ~410px, a stacking threshold, a pulse to hint the time step). All of those were symptoms of one premise — two things sharing one space — so the premise went instead of being patched further. Three things that look like details but aren't.

1. Day cells are a fixed 214px grid (7×28px) rather than flex:1 — a stretched cell with a fixed height renders as an oval under border-radius:50%, so a guaranteed square is what makes the circle a circle.

2. .bai-dt-col uses ::before/::after spacers so the first and last values can scroll to the centre band; without them you can't select 00 or 59. That's the empty space visible above 00 in the minutes column below — it's load-bearing, not a gap.

3. .bai-dt-done is display:none until .step-time — you can't confirm before you've reached the time step, so the button doesn't exist yet rather than sitting there disabled.

That objection doesn't transfer here: this surface auto-dismisses in 2.5–4 seconds (see below) and is not fixed — it is the exact pattern a phone's own notification uses over its status bar, briefly. Auto-dismiss duration is content-scaled, not fixed (designer: “two point five to four seconds depending on the content digestion”) — toastDuration() clamps 1400 + text.length * 45 to the 2500–4000ms window, so “+500 AI Credits” alone earns the floor and a title+subtitle pair earns more, never past the ceiling. This directly REVERSES the card's own "no timer, close button only" rule (rule 38 — a timer half-duplicates a close button on a surface read at the user's own pace); that reasoning held for a card, not for a banner whose entire idea is announce-then-leave, so the close button stays as the early-exit, not the only exit. REWARD reuses .tgm-ic-ok's literal recipe (ok wash + check glyph) rather than inventing a new "rewarding" colour — the designer asked for "something rewarding… maybe a tick mark," and this app already has exactly one vocabulary for that: the same chip .bai-dialog-ic uses. ALERT mirrors it at the danger token, 16% strength to match. Two states of ONE component, not two components. State-coloured LEFT EDGE + an icon-only PULSE, both added same day. The first pass differentiated the two states through the icon's 16% wash alone — faint by design, and on the same recipe an independent review had already measured at ~1.25:1 on a white card. A transient surface that has to read in one glance needed a stronger signal: a 3px border-left at FULL ok/danger strength (not a new idiom — .bai-sched-btn.danger etc. already carry state through border colour, just at 40% on all four sides; the edge is that same idiom scoped to one side so it doesn't fight the neutral --bai-line-2 every other card uses) plus a 2× entrance pulse on the icon chip only, reusing .bai-highlight-pulse's exact box-shadow-ring technique via a --toast-pulse custom property so one keyframe serves both colours. Row is align-items: center, not flex-start. Flex-start anchored the 22px icon to the row's TOP while the text block grew downward from that same edge — against a two-line reward (title+sub) the icon's true centre sat ~6px above the text block's. Two magic-number hacks existed to paper over exactly this (a 1px nudge on the body, negative margins pulling the close button toward the corner) and neither held once content length changed. Centering the row aligns every child to the same true centre with zero compensation, for 1 line or 2. Padding is a uniform 11px inset on all four sides as a result — border(1)+pad(10) on three sides, border-left(3)+pad-left(8) on the accent edge.

Conventions

Rules that hold across the system — worth reading before adding anything.

house rules
1. A signal must earn its slot. Before adding a divider, badge, or tag, name what already signals that boundary — a label's own margin, a card's border, a colour/weight shift, or a neighbouring line of text. A second element restating the first is decoration.
2. Match the ROLE, not the look. Reuse a component because it does the same job, not because it resembles what you need. An accent-tinted card that happens to look right may be a chat-message bubble, not a pricing card.
3. Every control renders every state. Empty, filled, active, disabled, hover. An interaction state that's missing — or borrowed from an unrelated colour — is a worse signal than none.
4. One hero action per surface. Filled + .hero weight for the action you're recommending; outlined and slimmer for the escape hatch. The size difference is doing work.
5. Spacing is hierarchy. Tight within a group, generous between groups. Beware stacking a child's own margin against a parent's flex gap — they add, they don't override, and that's how a label ends up further from what it labels.
6. Both themes, every time. A recipe tuned by eye on dark can read dull or smudged on light (and vice versa). Check contrast, not vibes.
